# Version-control tooling (husky + commitlint + commit-and-tag-version) — Design

**Date:** 2026-06-10
**Status:** Approved (pending spec review)

## Overview

Add commit-message enforcement and automated version bumping to
`@agentsoft/agent-chat`. Three tools:

- **husky** (v9) — manages the git hooks.
- **commitlint** (`@commitlint/cli` + `@commitlint/config-conventional`) —
  validates every commit message against the Conventional Commits spec.
- **commit-and-tag-version** — the maintained, drop-in fork of the deprecated
  `standard-version`. On `npm run release` it bumps the version, regenerates
  `CHANGELOG.md`, commits `chore(release): x.y.z`, and creates a git tag.

The project already writes conventional commits (`feat(cli):`, `fix:`, `docs:`),
so this formalizes an existing convention rather than introducing a new one.

## Goals

- Reject non-conventional commit messages at commit time (`commit-msg` hook).
- Run the type-checker and test suite before each commit (`pre-commit` hook).
- Provide a single `npm run release` that bumps the version, writes the
  changelog, commits, and tags — driven by commit history.
- Install the hooks automatically on `npm install` (via the `prepare` script).

## Non-goals

- **No npm publishing.** The package stays `private: true`; `release` only
  bumps/changelogs/tags locally. Pushing tags is a separate manual step.
- **No CI/CD release automation** (no release-please / GitHub Actions release
  flow). The release is local and manual by design.
- **No scope enum.** Commit scopes stay free-form; we do not lock them to a
  fixed list.
- **No changes** to the MCP server, bridge, or CLI runtime code.

## Why commit-and-tag-version (not standard-version)

`standard-version` was sunset by the conventional-changelog team in 2022 and is
archived (no fixes, accruing peer-dependency warnings). `commit-and-tag-version`
is its actively maintained fork with an **identical CLI, config format, and
behavior** — so the workflow the user asked for is preserved exactly, just on a
package that is still maintained.

## Components

### 1. Dev dependencies (added to `devDependencies`)

- `husky`
- `@commitlint/cli`
- `@commitlint/config-conventional`
- `commit-and-tag-version`

### 2. `package.json` script additions

```jsonc
{
  "scripts": {
    "prepare":   "husky",                          // sets up hooks on install
    "typecheck": "tsc -p tsconfig.json --noEmit",  // new; reused by pre-commit
    "release":   "commit-and-tag-version"          // bump + CHANGELOG + tag
  }
}
```

Existing scripts (`start:bridge`, `start:mcp`, `cli`, `build`, `test`,
`test:watch`) are unchanged.

### 3. `commitlint.config.js`

The package is `"type": "module"`, so the config is ESM. commitlint v19 loads
ESM config files natively.

```js
export default { extends: ["@commitlint/config-conventional"] };
```

This accepts the commit types already in use (`feat`, `fix`, `docs`, `chore`,
`refactor`, `test`, etc.) with free-form scopes. The existing git history is
already conformant.

### 4. Husky hooks

husky v9 hook files are plain shell scripts — the old
`#!/usr/bin/env sh` + `. "$(dirname -- "$0")/_/husky.sh"` boilerplate is no
longer required.

`.husky/commit-msg`:
```sh
npx --no-install commitlint --edit "$1"
```

`.husky/pre-commit`:
```sh
npm run typecheck && npm test
```

The pre-commit hook blocks a commit if the type-check or the test suite fails.
Both are fast on this project (pure-logic vitest suite + a small TS6 build).
The standard husky escape hatch — `git commit --no-verify` — bypasses the hooks
for emergencies; this is documented in the README.

### 5. `CHANGELOG.md`

Generated by `commit-and-tag-version`. The **first** run uses
`--first-release`, which seeds `CHANGELOG.md` from existing history **without**
bumping the current `0.1.0` version or creating a misleading bump. Subsequent
runs (`npm run release`) bump the version according to the commit types since
the last tag (fix → patch, feat → minor, breaking → major), append to the
changelog, commit, and tag.

### 6. README — "Commits & releases" section

A short section documenting:
- the Conventional Commits format (`<type>(<scope>): <subject>`),
- that hooks run on commit (commit-msg lints the message; pre-commit runs
  typecheck + tests), and `--no-verify` bypasses them,
- the release flow:
  ```bash
  npm run release            # bump version, write CHANGELOG, commit, tag
  git push --follow-tags origin release
  ```
  noting that `commit-and-tag-version` does **not** push automatically.

## Behavior details

- **Hooks install on `npm install`** via `prepare: "husky"`. After the initial
  setup `npm install`, `.husky/_/` exists and the two hook files are active.
- **`npm run release` is local and manual.** It never pushes and never
  publishes. The version bump is derived from commit history.
- **`private: true` is retained.** Nothing is published to a registry.

## Error handling / edge cases

- **Bad commit message** → `commit-msg` hook exits non-zero, commitlint prints
  the rule violations, the commit is aborted.
- **Failing typecheck or tests** → `pre-commit` exits non-zero, commit aborted.
- **Emergency bypass** → `git commit --no-verify` skips both hooks (documented).
- **First release with no prior tag** → use `--first-release` so all history is
  summarized into the initial changelog without an unintended version bump.

## Testing

This change is configuration and tooling; it has no unit-testable pure logic.
It is verified by integration checks (the "run it for real" approach):

1. `npm install` completes and creates `.husky/_/` with the two hook files.
2. `git commit -m "bad message"` is **rejected** by commit-msg (commitlint
   prints the violated rules).
3. `git commit -m "test: conventional message"` passes the message check.
4. A deliberately broken type or test makes `pre-commit` fail and aborts the
   commit; reverting it lets the commit proceed.
5. `npm run release --dry-run` reports the correct next version derived from the
   commits since the last tag, with no files modified.
