# Version-control tooling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add husky-managed git hooks that enforce Conventional Commits (commitlint) and run typecheck+tests before every commit, plus a `commit-and-tag-version`-driven `npm run release` for version bumping and changelog generation.

**Architecture:** Three dev tools wired through `package.json` and the `.husky/` hook directory. husky v9 installs hooks on `npm install` via the `prepare` script; `.husky/commit-msg` runs commitlint, `.husky/pre-commit` runs `npm run typecheck && npm test`; `commit-and-tag-version` provides `npm run release`. Ordering is load-bearing — dependencies and commitlint config must exist before the hooks that call them become active, otherwise the next commit fails.

**Tech Stack:** husky v9, @commitlint/cli + @commitlint/config-conventional, commit-and-tag-version, npm scripts, ESM (`"type": "module"`).

**Note on testing:** This is configuration/tooling with no unit-testable pure logic. Each task is verified by **integration checks** — running the real hook/CLI and observing accept/reject behavior — not by vitest tests. That is intentional and matches the approved spec (`docs/superpowers/specs/2026-06-10-version-control-tooling-design.md`).

### Task 5: Document commits & releases in the README

**Files:**
- Modify: `README.md` (insert a new section immediately before `## Development`)

- [ ] **Step 1: Insert the "Commits & releases" section**

In `README.md`, insert the following section immediately **before** the line `## Development`:

```markdown
## Commits & releases

Commits follow [Conventional Commits](https://www.conventionalcommits.org/):
`<type>(<scope>): <subject>` — e.g. `feat(cli): add install command`,
`fix(bridge): resolve recipient JID`. Common types: `feat`, `fix`, `docs`,
`refactor`, `test`, `chore`, `build`, `ci`.

Git hooks (installed automatically on `npm install` via husky) enforce this:

- **commit-msg** runs commitlint to validate the message format.
- **pre-commit** runs `npm run typecheck && npm test`.

Bypass the hooks in an emergency with `git commit --no-verify`.

Cut a release — bumps the version from commit history, regenerates
`CHANGELOG.md`, commits `chore(release): x.y.z`, and tags it. It does **not**
push or publish:

\```bash
npm run release                      # subsequent releases
npm run release -- --first-release   # only the very first time (no version bump)
git push --follow-tags origin release
\```
```

(Replace the `\`` escapes with real triple backticks when writing the file.)

- [ ] **Step 2: Verify the section renders and is placed correctly**

Run:

```
Expected: the "Commits & releases" line number is **less than** the "Development" line number (section precedes Development).

- [ ] **Step 3: Commit**

```bash

git commit -m "docs: document conventional commits and release flow"
```
Expected: hooks pass, commit succeeds.

### Task 6: Generate the initial CHANGELOG via the first release

> ⚠️ This task creates a **git tag `v0.1.0`** and a `chore(release): 0.1.0` commit on the current branch. It does not push. Reversible with `git tag -d v0.1.0 && git reset --hard HEAD~1` if needed.

**Files:**
- Create: `CHANGELOG.md` (generated)
- Modify: `package.json` (version unchanged at 0.1.0 under `--first-release`)

- [ ] **Step 1: Dry-run the release to preview**

Run:
```bash
npm run release -- --first-release --dry-run
```
Expected: prints the changelog it would generate and `tagging release v0.1.0`, and reports **no files changed** (dry run). Confirms the pipeline is wired correctly.

- [ ] **Step 2: Run the first release**

Run:
```bash
npm run release -- --first-release
```
Expected: generates `CHANGELOG.md` from existing history, stages it, makes a `chore(release): 0.1.0` commit (which passes pre-commit typecheck+test and commit-msg linting), and creates the `v0.1.0` tag. Version stays `0.1.0` (no bump under `--first-release`). Nothing is pushed.

- [ ] **Step 3: Verify the changelog and tag exist**

Run (three independent positive checks):
```bash
test -f CHANGELOG.md && echo "CHANGELOG.md exists"
git tag | grep -qx "v0.1.0" && echo "v0.1.0 tagged"
[ -z "$(git status --porcelain)" ] && echo "tree clean"
```
Expected: prints all three lines — `CHANGELOG.md exists`, `v0.1.0 tagged`, `tree clean` (commit-and-tag-version committed its own changes, so the tree is clean).

- [ ] **Step 4: Confirm a subsequent dry-run reports the next bump**

Run:
```bash
npm run release -- --dry-run
```
Expected: it reports what it would do (no commits to release, or the next version it would compute) and changes **no files** (dry run). This confirms `npm run release` is ready for future use.
